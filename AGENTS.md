# AGENTS.md

A brief guide to working in this repository. Only non-obvious, verified facts.

## Project structure
- A monorepo of two parts: `backend/` (Python/FastAPI) and `frontend/` (React + TS + Vite + Tailwind). There is no single root package manager; each part is built and deployed separately. `electron/` (desktop shell, see below) and `packaging/` (native build scripts, see `docs/PACKAGING.md`) are auxiliary.
- The main `README.md` (+ `README.ru.md`) is at the repo root; `docs/` holds `PACKAGING.md` (+ Russian mirror) and `docs/AGENTS.ru.md` — a translation of this file that may lag. `dist-packages/` at the root is the local output of the packaging scripts (gitignored build artifacts, not source).
- A single Docker image (multi-stage build): Node builds the SPA, Python + Caddy serve it. In production, `entrypoint.sh` runs → uvicorn (`:8000`) behind Caddy (`:80`); compose maps host `8888`→`80`. Caddy also proxies `/api/*` and `/proxy/*` to uvicorn and serves the SPA with a `try_files` fallback.

## How to run
- Full stack: `cp .env.example .env` (optional — credentials), then `docker compose up -d --build` → http://localhost:8888.
- Backend only (locally): `cd backend && pip install -r requirements.txt`, then `uvicorn app.main:app --reload --port 8000`. Health check — `GET /api/health`.
- Frontend only (locally): `cd frontend && npm install && npm run dev` → http://localhost:5173, which proxies `/api` to `:8000` (see `vite.config.ts`). The frontend expects the backend to be running separately; there is no built-in mock.

## Configuration / environment
- Settings via `VIPER_*` environment variables, loaded by pydantic-settings (`backend/app/config.py`). `.env` is read automatically if present. The password is `VIPER_PASSWORD_MD5` (vBulletin sends md5(password), not plaintext).
- Three different forum domains in the config: `forum_base_url`=`viper.to` (parsing of sections/threads), `click_base_url`=`viper.click` (clean XML, the preferred path), `login_base_url`=`vipergirls.to` (vBulletin login). Do not conflate them.
- The effective `forum_base_url` can be **overridden at runtime** by the `forum_proxy` setting (PUT `/api/settings`) — a list of mirrors in `FORUM_DOMAINS` (`settings_service.py`: planetviper.club, viperbb.rocks, viperkats.eu, etc.). Do not edit the config if the actual request domain is suddenly different — first check the `settings` table in SQLite.
- Proxy server: runtime setting `proxy_enabled` (bool, default `true`) + `proxy_url` + optional `proxy_username`/`proxy_password` (PUT `/api/settings`). `settings_service.get_proxy_url()` reads `proxy_enabled` as its first check — when `false`, it returns `""` (direct), **without overwriting** the stored URL/credentials (the user can toggle the proxy back on without re-entering them). Otherwise it builds a single URL like `socks5://user:pass@host:port` (credentials URL-encoded), applied to **both** upstream clients — the forum `curl_cffi.AsyncSession` (`scrapers/http.py`, `proxies={"http":..,"https":..}`) and the image-hosts `httpx.AsyncClient` (`hosts/base.py`, `proxy=...`). Supported: `socks5://`, `socks5h://` (DNS via proxy), `http://` (socks5 requires the extra `httpx[socks]` → the `socksio` package, already in `requirements.txt`). **`socks5://` is normalised to `socks5h://`** inside `get_proxy_url()`: with plain socks5 libcurl resolves DNS locally and only the connection is proxied — when the forum is blocked by DNS (the typical reason for a proxy here) the local resolver returns a poisoned IP and the proxied connect times out ("can't connect with proxy on"); socks5h sends the hostname to the proxy (httpx's socksio always does ATYP=3 anyway, so the rewrite is semantically a no-op for it). A bare `host:port` (no scheme) also defaults to SOCKS5 — the UI never asks the user for a scheme. The session/client is recreated whenever any of these four settings changes at runtime (tracked by the composed URL in `_proxy_url` in each module). The password is redacted in logs via `redact_proxy()`.
- Concurrency/cache tuning — env `VIPER_*` vars are **first-boot seeds** for the runtime `settings` table: `settings_service._ensure_loaded()` writes a key absent from the DB **only when the var was explicitly set** (detected via pydantic `model_fields_set` — an unset default never writes a row, so later code-default changes still reach fresh installs). Once the row exists (seeded here or set via UI/`PUT /api/settings`), the DB wins forever and the env var is ignored. Seeded keys: `download_concurrency`, `thread_concurrency`, `download_timeout`, `max_retries`, `cache_limit_gb`. Env-only knobs (no runtime override, change needs a restart): `request_limit` (default 2 req/s, a leaky-bucket **per destination host** — `HttpClient._rate_for()` in `scrapers/http.py` keeps one `RateLimiter` per hostname, so viper.to and viper.click don't serialize behind one bucket), `search_request_limit` (4.0, a separate ceiling for multi-series fan-out search), `per_host_concurrency` (2, **active** — a separate `asyncio.Semaphore` per image host in `image_proxy._HOST_SEMAPHORES`, on top of the global one; a single dead/slow host cannot monopolize the shared budget). Runtime values: `download_concurrency` (8, **dynamic** — `image_proxy._get_proxy_semaphore()` reads the runtime setting and recreates the `asyncio.Semaphore` on change; a shared budget for interactive browsing AND the download queue's per-image fetch via `fetcher.process_image`), `thread_concurrency` (controls batch covers in `thread_service.get_thread_covers_batch` + the parallel worker limit in the download queue `_worker_loop`), `cache_limit_gb` (float, default 0 = unlimited; when >0 the maintenance loop LRU-trims `cache/img` by mtime — `image_proxy.cleanup_cache()` via `trim_cache_if_needed()`). Two more runtime settings: `auto_download` (bool, default `true` — new queue items start as `queued` and are picked up by the worker; off → added as `stopped`, manual START required) and `auto_clear_completed` (bool, default `false` — when on, a fully-downloaded thread is auto-removed from the queue). `settings_service._SCHEMA` has 13 keys (`_coerce` supports a float branch). The old dead `VIPER_CACHE_MAX_GB`/`cache_max_gb` was removed; the stats wire field is now `cache_limit_gb`.
- The `resolved_url` mapping is cached in `images.resolved_url` (schema in `db.py`) via `_resolve_row` (`image_proxy.py`) — repeat cache-misses skip the interstitial-resolution RTT (1 request per host instead of 2). On top of that, `image_proxy` keeps an in-process **row LRU** (`_row_cache`, OrderedDict, max 8192): `get_image_row(id)` serves /api/image lookups without touching SQLite; `set_resolved_url_cache()`/`put_image_rows()` let `download_jobs` write through. `_resolve_row` takes a dict (usually the cached row itself) and mutates it. Re-parsed threads get NEW autoincrement image ids, so stale LRU entries are only wasted memory.
- **SQLite access goes through a bounded connection pool** (`db.py`: `_Pool`, size 8, `get_db()` returns a `_PooledDb` whose `close()` recycles the connection — idempotent). Per-connection PRAGMAs: `busy_timeout=5000`, `synchronous=NORMAL`, `foreign_keys`, `mmap_size=256MB`, `cache_size=-65536`; WAL is set once in `init_db` (persistent). `close_pool()` runs on app shutdown (main.py lifespan). **Never nest `get_db()` while holding another connection** — the pool blocks on a semaphore and will deadlock. `thread_service.list_threads`/`get_thread_detail` open short-lived conns around network scrapes for exactly this reason (a pooled conn must not be pinned across a multi-second rate-limited fetch).
- **Run uvicorn single-process only** (`launcher.py` has no `--workers`): the circuit breaker, inflight single-flight locks, the settings in-memory cache, row LRU and all semaphores are module-level state — multiple workers would fork it and behave inconsistently.
- `DATA_DIR` (default `/data`) contains `viper.db` (SQLite, the working cache — grows with usage, not a fixed size) and `cache/` (downloaded image previews). In Docker this is the `./data` volume. There are NO migrations — `init_db()` creates tables at startup; do not wipe `data/` without reason.

## Backend layout (not obvious from the file names)
- `app/scrapers/` — forum parsing: `viper_click.py` (preferred, clean XML), `forumdisplay.py`/`auth.py` (direct `viper.to` fallback via `curl_cffi` to bypass Cloudflare). `auto_login()` at startup: if env credentials are set (`VIPER_USERNAME`/`VIPER_PASSWORD_MD5`) — it logs in; otherwise `restore_auth()` restores the session from `DATA_DIR/auth.json` (cookies + username, chmod 0600; written by `login()` on UI login, deleted by `logout()`). No network check (optimistic) — invalidation surfaces on the first auth-required action. In `forumdisplay.py`, IMPORTANT sticky threads (rules/guidelines/announcements) are dropped BEFORE truncation to `PER_PAGE` (12; search — `search.py`: `_PAGE_SIZE=60`, `_UI_PER_PAGE=12`, 5 UI pages per merge-block) — otherwise in forums with 7+ such threads (e.g. forum 308) the user saw 5 cards instead of 12, because the downstream filter `_is_non_photoset` (`thread_service.py`) discarded them post-truncation.
- `app/hosts/` — `registry.py` (host identification by URL substring from `HOST_TABLE`, 16 hosts) and `base.py` (HTTP client + all interstitial-page resolvers in `_RESOLVERS`). Adding a host = a new resolver in `base.py` + a row in `HOST_TABLE` (`registry.py`). Pixhost: the substring `pixhost` covers both the `.to` **and** `.cc` mirrors (both are identified as `pixhost.to`); `resolve_pixhost` does a pure URL-transform `show/{a}/{f}`→`img2.pixhost.to/images/{a}/{f}` with no HTTP/DNS (the apex `pixhost.to` suffers intermittent DNS failures). imx.to: `resolve_imx_thumb()` rewrites any dead imx.to thumb prefix → the live CDN `https://image.imx.to/u/t/` (pure URL-transform, no HTTP); `image_proxy.py`'s thumb branch uses it when host=="imx.to". `image_proxy` serves every tier **download-then-serve**: the upstream file lands in the extension-less content-addressed disk cache first (`_ensure_full_cached`, single-flighted per cache key in `_INFLIGHT_LOCKS`), then goes out as a `FileResponse` — honest 502s instead of truncated 200s, and concurrent requests share one upstream fetch. Upstream content-types are remembered in `_content_types` (bounded OrderedDict) because cache files carry no extension. The medium tier (`?size=medium`) is a ≤800px WebP (`method=2`) generated single-flighted by `_ensure_medium`; `_create_medium` uses JPEG `draft()` decoding + `exif_transpose`; GIFs bypass the resize (animation would collapse to one frame). On a total resolve/fetch failure, `image_proxy._serve_thumbnail` serves the thumb as a degraded mode (e.g. turboimagehost behind a CF JS-challenge — the full image is only available via the thumb-CDN); NOTE: `_serve_thumbnail` deliberately does NOT check `is_host_dead` — OLD threads have their thumbs on the same dead host (`s4d*.turboimagehost.com`), so the breaker would block the reachable thumb; the thumb is always attempted as the fallback. The "Stage 5" note in `registry.py` is a refactoring plan, not a missing feature.
- The circuit breaker (`hosts/circuit.py`) marks frequently failing hosts as "dead" → `/api/image/{id}` instantly returns 502 `Host temporarily unavailable` **without** attempting a request. Do not conflate this with a real resolve/fetch error when debugging 502s.
- A background maintenance task (`_maintenance_loop` in `main.py`, every 30 min after startup) calls `image_proxy.trim_cache_if_needed()` — an LRU-by-mtime trim of `cache/img` that only runs when the runtime setting `cache_limit_gb` > 0 (default 0 = unlimited; hardlinked downloads survive the trim). `/api/stats` reports the current cache size (measured via `asyncio.to_thread`, never on the event loop) and the effective limit (field `cache_limit_gb`).
- `app/services/` — `zip_service.py` (streaming on-the-fly ZIP packaging via `stream-zip`), `image_proxy.py`, `thread_service.py`, `download_queue.py` (the **active** download system — persistent `download_queue` SQLite table + `_worker_loop` that spawns up to `thread_concurrency` threads in parallel; see below), `fetcher.py` (the shared image-fetch pipeline, extracted from the removed legacy job system: `get_thread_images`/`thread_title`/`resolve_row`/`download_with_retry`/`process_image` — resolve to a direct URL with DB/LRU write-through + content-addressed-cache download with retries; the per-image fetch shares the global `download_concurrency` semaphore), `library.py` (likes + download history: `post_thanks_add/remove` via `_get_securitytoken`, `record_download`/`list_downloads` with pruning of folders absent from disk, get/set `downloads_folder`; the `db.py` tables `liked_threads` + `downloads`), `settings_service.py` (runtime settings via `/settings`).
- API routers live in `app/api/`, all mounted under the `/api` prefix (see `main.py`). `GET /api/thread/{id}/cover` returns the cover + the first 5 previews for the hover carousel. For bulk loading of a card list there is `POST /api/threads/covers` (body `{thread_ids:[...]}` → `{covers: {"<id>": <CoverOut|null>}}`) — one request instead of N parallel `/cover` calls, it does not exhaust the browser's connection pool and does not queue behind the forum's rate limiter. The `/api/image/{id}?size=thumb|medium|full` and `/api/proxy?url=...` (proxy an arbitrary URL) endpoints are large streams; Caddy proxies `/api/*` and `/proxy/*` to uvicorn with `flush_interval -1`. A thread-detail request also fires background `fire_background_task` jobs: `prefetch_resolution` (resolves up to 20 direct URLs so the first image views skip the interstitial RTT, from `thread_service.get_thread_detail`) and `prewarm_mediums` (downloads + renders the medium for the first 6 images, from `api/threads.py`). Image responses carry `Cache-Control: immutable` (1-year, content-addressed URLs).
- `GET /api/search?q=...&forums=...` is a **live** search of the forum (vBulletin Advanced Search, not over the cache): on a scoped request it fans out across batches of leaf forums with a merge (`scrapers/search.py`). Sort is now monotonic — `_SearchSession._key()` uses post_id/thread_id (was a parsed human date string → jumbled order); `search_forum` adds a defensive slice sort. Results are enriched with cached covers. See the separate `search_request_limit`.
- **Download queue** (the active system, `services/download_queue.py` + `api/download_queue.py`): a persistent SQLite `download_queue` table (thread_id PK, title, status[queued|downloading|stopped|done|error], total/completed/failed counters, error, added_at; ordered by `_rowid_`) + a background `_worker_loop` (every 2s) that spawns up to `thread_concurrency` threads in parallel (claims via status=downloading before spawn), reaps finished tasks, and flushes live `_progress` to DB. `_download_thread(tid)` reuses `process_image` from `fetcher.py` (shares the global `download_concurrency` semaphore with live browsing), then materializes to `downloads_folder` + `record_download` on completion → status=done. Cooperative STOP: `request_stop(tid)` → `task.cancel()` → `CancelledError` caught → status=stopped (resume reuses cached files); `fetcher.download_with_retry` also closes resp + unlinks the partial file on CancelledError (no partial left behind). `add_to_queue(ids)` is idempotent and honors `auto_download` (queued if on, stopped if off). `on_startup()` (called from `main.py` lifespan after `auto_login`) orphans any `downloading` rows → stopped and starts the worker. API: `GET /api/download/queue`, `POST /api/download/queue` {thread_ids}, `POST /api/download/queue/{tid}/stop`, `POST /api/download/queue/{tid}/start`, `DELETE /api/download/queue` (clear all). The legacy job system (`POST /api/download/multi` → `/status` → `/retry` → `/zip`) was removed entirely; `api/download.py` now only serves the one-off `GET /api/thread/{id}/download` stream.
- Likes/downloads (`api/library.py`): `POST/DELETE /api/thread/{tid}/like` (401 if not logged in; under the hood `post_thanks.php` + securitytoken), `GET /api/liked`, `GET /api/downloads` (items + folder), `POST /api/downloads/folder` (the folder is reported by Electron on startup/change).
- Forum request limiting is a leaky bucket **per destination host** (`HttpClient._rate_for()` in `scrapers/http.py`; see `request_limit` / `search_request_limit` above). Exception: search fan-out uses its own module-level `_search_rate = RateLimiter(search_request_limit)` in `scrapers/search.py` — one shared limiter, not per-host. Do not hammer endpoints in loops.
- uvicorn itself serves the built SPA from `backend/static/` if the directory exists (`StaticFiles` on `/`, see `main.py`) — a fallback for when Caddy is not used. In production this is handled by Caddy from `/srv/static`.
- The `_NoCacheHTMLMiddleware` (`main.py`, a **pure ASGI class** — not `BaseHTTPMiddleware`, which wraps every request in an extra task and hurts the big streaming image responses) sends `Cache-Control: no-cache` **only for `index.html`**: Vite gives assets content-hashed names (they can be cached forever), but the SPA shell must be re-read — otherwise after an upgrade the browser calls old hashes → 404 → white screen (Electron duplicates this by clearing the cache at startup, see below).

## Frontend
- The alias `@` → `./src` (vite + tsconfig). Data — TanStack Query (staleTime 60s, `refetchOnWindowFocus: false`); routing — `react-router-dom` v7. No state library — state is React `useState` + the Query cache + localStorage-backed hooks (`useViewMode`); follow that pattern, don't introduce a store.
- `npm run build` is `tsc -b && vite build` — TypeScript must pass before the bundle is built. The build output is `frontend/dist` (served by Caddy in Docker). API base is overridable at build time via `VITE_API_BASE` (`src/api/client.ts`, default same-origin). Because image responses are 1-year `immutable`, `client.ts` appends a `_v=<token>` cache-bust param (sessionStorage token) to image URLs; `clearImageCache()` bumps the token AND drops Cache Storage — a server-side cache clear alone would leave stale immutable files in browsers.
- ThreadPage loads the WHOLE thread at once (`thread.images`, all posts) and paginates only by **12 images per page** (`IMAGES_PER_PAGE=12`, `frontend/src/pages/ThreadPage.tsx`) — the flat image list is sliced into 12-image pages, each rendered grouped by post (heading "Post N" + grid); the per-post index is derived from first-appearance order of `post_id`. There is NO post pagination anymore (it used to fetch 5 posts/page via `api.threadPosts`; the backend `/thread/{id}/posts` endpoint still exists but the UI no longer calls it). `VirtualImageGrid`/`react-window` are NO LONGER used in ThreadPage (max 12 nodes — virtualization is unnecessary). Numeric pagination is the reusable `components/Pagination.tsx` (first/‹/window of 5 pages/›/last), duplicated top+bottom on Category/Search/Thread.
- The Lightbox (`components/Lightbox.tsx`) preloads neighboring full images (`new Image()` for ±1) during navigation — the browser deduplicates against the immutable cache, so this is a no-op if they were already loaded. Preloading is **skipped** when `navigator.connection.saveData` is on or effectiveType is 2g (`PRELOAD_NEIGHBOURS`, module-level). **Slideshow**: a Play/Pause toggle + a 1–5s interval slider; when on, auto-advances through images and loops at the end. The Lightbox receives the WHOLE thread's flat image list — navigation spans the entire thread, not just the visible 12.
- **DOM-level keep-alive for CategoryPage** (`App.tsx` + `main.tsx`): `/` and `/forum/:forumId` are registered in the route table only as empty-fragment placeholders; CategoryPage itself is not a route element — App detects `/forum/:forumId` via `matchPath` and always keeps CategoryPage mounted, toggling visibility with the `hidden` CSS class. Hence returning from a thread is instantaneous (without reloading images or scroll position). `cachedForumId` stores the last forum while the user is in a thread. The Outlet renders `/thread/*`, `/search`, `/liked`, `/downloads`.
- `RetryImage.tsx` — a drop-in `<img>` with auto-retry (cache-bust + 3 attempts), a red ✕ fallback, and a manual-reload button on hover. If the `className` already contains a position utility (absolute/relative/fixed/sticky), it does NOT add its own `relative` (Tailwind orders `.relative` after `.absolute`, which breaks the hover carousel — see the `positionClass` helper). It registers itself in the global `ImageRefreshProvider` for batch-reloading failed images.
- **Cards use `size=thumb`** (50-200KB) initially, NOT medium — a thumb is enough for cards, and the backend does not need to download the full (5-20MB) image for a Pillow resize. `fetchPriority="high"` on the cover, `"low"` on previews (eager; camelCase prop — React 18.3+ supports `fetchPriority` natively, older 18.x needs the lowercase attr). In the `ThreadPage` grid — medium (a larger view there). In the Lightbox — full + preload of neighbors via `new Image()`.
- **Card grids** (`CategoryPage`/`SearchPage`/`LikedPage`/`DownloadsPage`): adaptive `grid-cols-2 sm:grid-cols-3 lg:grid-cols-3 xl:grid-cols-4`, landscape covers with `aspect-[4:3]` and `object-contain` (vertical images get side bars, not cropped). `RetryImage` forwards `object-fit` from the className to the inner `<img>` (default `object-cover` — see the `objectFitClass` helper next to `positionClass`). The heart-shaped like button sits **top-left** on the card and uses the `useLikes` hook (optimistic, `POST/DELETE /api/thread/{tid}/like`); a download button sits **top-right** (adds the thread to the download queue via `POST /api/download/queue`). `ThreadCard` is defined inline in `CategoryPage` and reused by SearchPage/LikedPage; DownloadsPage renders its own inline card (no like/download buttons, `size=medium`, `refetchOnMount: "always"` — the backend prunes deleted folders on GET). Card covers arrive via `hooks/useOrderedCovers.ts`: ONE batch `POST /api/threads/covers` for threads lacking server-cached `image_ids` (threads that have them are seeded instantly, no request); a failed/aborted batch settles pending entries to `null`.
- **Wave-based card loading** (`hooks/useWaveLoader.ts`, the coordinator lives in `CategoryPage`/`SearchPage`; `ThreadCard` itself is defined **inline** in these pages, not as a separate file): loading is synchronized across **all cards on the page**, not per-card. `MAX_SLOTS=5` (cover=slot 0 + 4 previews). The coordinator holds `step` 0..9 and advances it when a **90% quorum** of cards reports completion of the current slot (`reportCardDone`, `quorumCount` = ceil, min 1 — one dead host no longer stalls the whole page); an 8-second timeout (`WAVE_TIMEOUT_MS`) guards against a stuck slot. **Phase 1 (thumb, step 0–4):** slot 0 of all cards in parallel → slot 1 → …; within a single card — strictly sequential. **Phase 2 (medium, step 5–9):** the same wave pattern for the medium of **slot 0 (the cover) only**, via a background `new Image()` probe; slots > 0 auto-report and their medium is deferred to card hover (the separate hover probe DOES clean up with `probe.src=""` — do not confuse it with the wave probe). Once the medium is downloaded (into the browser cache), the visible `<img>` switches thumb→medium instantly + a short flash animation (`img-swap-flash`, the `swapped` flag in `useImageRetry`). The wave starts only when all covers have been received (`coverById.has` for each `t.id`). `useImageRetry` does NOT reset `loaded` when the src changes — the browser keeps the thumb while the medium loads (no white flash); a failed medium probe leaves the thumb visible. No backend jobs/SSE — medium on demand via `/api/image/{id}?size=medium`. **The wave effect must NOT abort in-flight probes on step advance** (no `probe.src=""` cleanup): with a 90% quorum the wave routinely advances while the slowest card's probe is still in flight, and aborting it would leave that slot permanently unloaded (nothing revisits earlier slots) — an eternal card spinner / blank preview. The probe is allowed to finish in the background (`finish()` marks the slot ready whenever it lands; `pendingProbeRef` deduplicates across effect re-runs, `aliveRef` suppresses reports after unmount).
- `App.tsx` prefetches the `settings` and `stats` queries on mount — so that the Settings modal opens instantly even when image streams have taken up all 6 connections (TanStack Query deduplicates with the modal).
- **Header**: a Back button (`navigate(-1)`) replaces the old "Browse Photo Sets" label — there is no global title in the header anymore.
- **Download queue panel** (`components/DownloadQueuePanel.tsx`): a toolbar button with an active-count badge → dropdown table (title, status badge, [completed/total], progress bar, STOP/START per row — START hidden when done, Clear-queue button). Polled every 1s while there are active (`queued`/`downloading`) items. **Replaced** the old `MultiDownloadModal` non-dismissable popup (removed).

## Electron / desktop
- `electron/main.js` (the primary mode for end users per the README) spawns the backend as a child process and renders the SPA in a `BrowserWindow`; `electron/preload.js` (contextBridge) exposes `window.electronAPI` (`isElectron`, `showInFolder`, `openPath`, `chooseDownloadsFolder`). Launch: `python -m app.launcher --no-gui` with cwd `backend/`.
- **Backend reuse**: Electron first hits `/api/health`; if a backend is already listening (e.g. a systemd service from a deb/rpm), it does NOT spawn a second one (otherwise `address already in use`). On close it kills only the process it spawned itself (`startedBackend`).
- **Downloads into folders (desktop)**: `session.defaultSession.on('will-download')` → `item.setSavePath(downloadsDir/<filename>)` without a dialog (filename from Content-Disposition; default folder `~/Downloads/ViperGirls`, overridden via `dialog.showOpenDialog` over the IPC `choose-downloads-folder`, persisted in the settings `downloads_folder`). IPC `open-folder` → `shell.openPath` with an `fs.existsSync` check → graceful `{ok,missing}` (the frontend shows an alert + invalidates the list for pruning). IPC `show-in-folder` → `shell.showItemInFolder` (legacy).
- `backend/app/launcher.py` — the single server entrypoint for desktop and systemd (`packaging/common/run.sh`). `VIPER_HOST`/`VIPER_PORT` (default `127.0.0.1:8000`). `--no-gui` is now a **no-op** (server-only always) — kept for backward compatibility.
- **Python bundling differs by OS** (a gotcha when debugging native builds): on **Linux** the bundle sets `PYTHONHOME`+`PYTHONPATH` to its own runtime; on **Windows** the embeddable Python uses `python312._pth`, which **ignores `PYTHONPATH`** — the path to the backend is baked into the `._pth` at build time (see `packaging/docker/windows/Dockerfile`). Do not set `PYTHONHOME` on the Windows embeddable — it breaks.
- The menu is hidden (`Menu.setApplicationMenu(null)`); DevTools — **F12** via `before-input-event`. `WM_CLASS` is pinned to `vipergirls-viewer` so the taskbar/dock matches it to the `.desktop` and icon (`nativeImage`; a bare path is unreliable on Linux).
- On startup Electron clears the Chromium HTTP cache (`session.clearCache()`) — otherwise a cached `index.html` from a previous build references old content-hashed hashes → 404 → white screen. The backend duplicates this with the `_no_cache_html` middleware.
- Native packaging (exe/deb/rpm/AppImage) — cross-compiled from Linux via Docker, scripts in `packaging/scripts/` (details in `docs/PACKAGING.md`). A separate process from the self-host Docker image.

## Conventions / gotchas
- Backend unit tests live in `backend/tests/` (pytest + pytest-asyncio, `asyncio_mode=auto` via `pytest.ini`, deps in `requirements-dev.txt`). They cover **pure logic only, no network**: settings schema/coercion/persistence, proxy-URL composition + `redact_proxy`, the pure URL-transform resolvers (imx/pixhost), the host registry, the SQLite pool recycling, and the rate limiter. `conftest.py` points `DATA_DIR` at a temp dir **before any `app.*` import** (it is read at module import time), wipes the `settings` table per test, and recreates the settings-service `asyncio.Lock` (each test gets a new event loop). Run: `cd backend && pip install -r requirements.txt -r requirements-dev.txt && pytest`. There are NO frontend tests and no lint config beyond `tsc -b`. CI: `.github/workflows/build-macos.yml` (pushes to `develop`, PRs, manual `workflow_dispatch`; arm64-only `macos-14`, Intel dropped): a macOS-only **smoke-test gate** — `frontend npm run build`, `pip install`, then `python -m app.launcher --no-gui` must serve `GET /api/health` 200 within 60s; PyInstaller bundle best-effort (`continue-on-error`); and `.github/workflows/tests.yml` (same triggers; Ubuntu — matches the Docker image platform: pytest + frontend build + the same offline health smoke). Backend startup is offline-safe (no credentials + no `auth.json` → `auto_login`/`restore_auth` are no-ops, health reachable without network) — the same recipe works for local verification. (This is a git repository, branch `develop`.)
- **Manual UI testing**: the agent cannot click through the UI itself — it provides step-by-step instructions (what to click, what should happen, which logs to collect), and a human verifies in the running application and returns the result/logs. Backend changes are verified via `pytest` (unit scope) + `py_compile` + `import app.main` + isolated scripts on a test DB (`DATA_DIR=/tmp/opencode/...`), frontend — via `npm run build` (`tsc -b && vite build`).
- `.gitignore` and `.dockerignore` exclude `data/`, `.env`, `node_modules/`, `dist/`, `__pycache__` (git also ignores `dist-packages/`). `data/` is NOT in git (`git ls-files data/` is empty) — in the working tree it is live state: the growing `viper.db` (gigabytes) and the `cache/` of previews; treat it as runtime data, not source. The root `node_modules/` (there is no root package.json) is the opencode tool's own runtime, not a project dependency; the real frontend manifest is `frontend/package.json`.
- The build script copies `frontend/dist` out of the build stage; if you change the frontend, the Docker image must be rebuilt (`docker compose up -d --build`) — the `npm run dev` dev mode is separate from what Caddy serves.
- The parser targets external adult-forum sites; expect breakage when markup or Cloudflare rules change. Image hosts resolve interstitial pages on the fly (see `hosts/`).
- Native packaging is described in detail in `docs/PACKAGING.md` (see also the "Electron / desktop" section).
