# AGENTS.md

Краткое руководство по работе в этом репозитории. Только неочевидные, проверенные факты. (Перевод корневого `AGENTS.md`; оригинал — источник истины.)

## Структура проекта
- Монорепозиторий из двух частей: `backend/` (Python/FastAPI) и `frontend/` (React + TS + Vite + Tailwind). Единого корневого менеджера пакетов нет; каждая часть собирается и разворачивается отдельно. `electron/` (десктоп-оболочка, см. ниже) и `packaging/` (скрипты нативных сборок, см. `docs/PACKAGING.md`) — вспомогательные.
- Главный `README.md` (+ `README.ru.md`) лежит в корне репозитория; в `docs/` — `PACKAGING.md` (+ русское зеркало) и `docs/AGENTS.ru.md` — перевод этого файла, может отставать. `dist-packages/` в корне — локальный вывод упаковочных скриптов (гитигнорируемые артефакты сборки, не исходники).
- Один Docker-образ (многоэтапная сборка): Node собирает SPA, Python + Caddy её обслуживают. В проде запускается `entrypoint.sh` → uvicorn (`:8000`) за Caddy (`:80`); compose маппит хост `8888`→`80`. Caddy также проксирует `/api/*` и `/proxy/*` на uvicorn и отдаёт SPA с фолбэком `try_files`.

## Как запустить
- Весь стек: `cp .env.example .env` (опционально — учётные данные), затем `docker compose up -d --build` → http://localhost:8888.
- Только backend (локально): `cd backend && pip install -r requirements.txt`, затем `uvicorn app.main:app --reload --port 8000`. Проверка здоровья — `GET /api/health`.
- Только frontend (локально): `cd frontend && npm install && npm run dev` → http://localhost:5173, который проксирует `/api` на `:8000` (см. `vite.config.ts`). Frontend рассчитывает, что backend запущен отдельно; встроенного мока нет.

## Конфигурация / окружение
- Настройки через переменные окружения `VIPER_*`, загружаемые pydantic-settings (`backend/app/config.py`). `.env` читается автоматически, если присутствует. Пароль — `VIPER_PASSWORD_MD5` (vBulletin отправляет md5(password), а не открытый текст).
- Три разных домена форума в конфиге: `forum_base_url`=`viper.to` (парсинг разделов/тем), `click_base_url`=`viper.click` (чистый XML, предпочтительный путь), `login_base_url`=`vipergirls.to` (vBulletin-логин). Не путайте их.
- Эффективный `forum_base_url` может быть **перекрыт в рантайме** настройкой `forum_proxy` (PUT `/api/settings`) — список зеркал в `FORUM_DOMAINS` (`settings_service.py`: planetviper.club, viperbb.rocks, viperkats.eu и др.). Не правьте конфиг, если реальный домен запросов вдруг другой — сначала проверьте таблицу `settings` в SQLite.
- Прокси-сервер: runtime-настройка `proxy_enabled` (bool, по умолч. `true`) + `proxy_url` + опциональные `proxy_username`/`proxy_password` (PUT `/api/settings`). `settings_service.get_proxy_url()` первой проверкой читает `proxy_enabled` — когда `false`, возвращает `""` (напрямую), **не затирая** сохранённые URL/учётки (юзер может включить прокси обратно без повторного ввода). Иначе собирает единый URL вида `socks5://user:pass@host:port` (учётки URL-encoded), применяется к **обоим** upstream-клиентам — форумный `curl_cffi.AsyncSession` (`scrapers/http.py`, `proxies={"http":..,"https":..}`) и хостов изображений `httpx.AsyncClient` (`hosts/base.py`, `proxy=...`). Поддерживаются `socks5://`, `socks5h://` (DNS через прокси), `http://` (для socks5 требуется extra `httpx[socks]` → пакет `socksio`, уже в `requirements.txt`). **`socks5://` нормализуется в `socks5h://`** внутри `get_proxy_url()`: с чистым socks5 libcurl резолвит DNS локально и через прокси идёт только соединение — когда форум заблокирован по DNS (типичная причина прокси здесь), локальный резолвер отдаёт отравленный IP и проксированное соединение висит до таймаута ("can't connect with proxy on"); socks5h отправляет hostname прокси (у socksio в httpx и так всегда ATYP=3, так что перезапись для него семантически no-op). Голый `host:port` (без схемы) тоже по умолчанию SOCKS5 — UI никогда не просит юзера схему. Сессия/клиент пересоздаются при изменении любой из этих четырёх настроек в рантайме (трекается composed-URL в `_proxy_url` в каждом модуле). Пароль реда́ктируется в логах через `redact_proxy()`.
- Тюнинг concurrency/кэша — env-вары `VIPER_*` теперь **seed'ы первой загрузки** для runtime-таблицы `settings`: `settings_service._ensure_loaded()` пишет ключ, отсутствующий в БД, **только когда вар выставлен явно** (детект через pydantic `model_fields_set` — невыставленный дефолт никогда не пишет строку, поэтому последующие изменения кодовых дефолтов доходят до свежих установок). Как только строка существует (засеяна тут или через UI/`PUT /api/settings`) — БД побеждает навсегда, env игнорируется. Засеиваемые ключи: `download_concurrency`, `thread_concurrency`, `download_timeout`, `max_retries`, `cache_limit_gb`. Env-only ручки (без runtime-override, смена требует рестарта): `request_limit` (по умолч. 2 запр/сек, leaky-bucket **на хост назначения** — `HttpClient._rate_for()` в `scrapers/http.py`, один `RateLimiter` на hostname, viper.to и viper.click не сериализуются за одним бакетом), `search_request_limit` (4.0, отдельный потолок fan-out поиска), `per_host_concurrency` (2, **активный** — отдельный `asyncio.Semaphore` на каждый image-host в `image_proxy._HOST_SEMAPHORES`, поверх глобального; один мёртвый/медленный хост не монополизирует бюджет). Runtime-значения: `download_concurrency` (8, **динамический** — `image_proxy._get_proxy_semaphore()` читает настройку и пересоздаёт `asyncio.Semaphore`; общий бюджет для просмотра И per-image fetch очереди через `fetcher.process_image`), `thread_concurrency` (batch covers в `thread_service.get_thread_covers_batch` + лимит воркеров очереди), `cache_limit_gb` (float, 0 = без лимита; когда >0 maintenance-цикл LRU-тримит `cache/img` по mtime). Ещё две runtime-настройки: `auto_download` (bool, по умолч. `true` — новые элементы очереди стартуют `queued`; выключено → `stopped`, нужен ручной START) и `auto_clear_completed` (bool, по умолч. `false` — при on скачанный тред авто-удаляется из очереди). `settings_service._SCHEMA` — 13 ключей (`_coerce` с float-веткой). Старый мёртвый `VIPER_CACHE_MAX_GB`/`cache_max_gb` удалён; wire-поле stats теперь `cache_limit_gb`.
- Mapping `resolved_url` кэшируется в `images.resolved_url` (схема в `db.py`) через `_resolve_row` (`image_proxy.py`) — повторные cache-miss'ы пропускают interstitial-resolution RTT (1 запрос на хост вместо 2). Поверх этого `image_proxy` держит in-process **row LRU** (`_row_cache`, OrderedDict, max 8192): `get_image_row(id)` обслуживает lookup'ы /api/image без SQLite; `set_resolved_url_cache()`/`put_image_rows()` позволяют `download_jobs` писать сквозь (write-through). `_resolve_row` принимает dict (обычно сам закэшированный row) и мутирует его. Перепарсенные треды получают НОВЫЕ autoincrement image-id, так что устаревшие LRU-записи — лишь потраченная память.
- **Доступ к SQLite идёт через ограниченный пул соединений** (`db.py`: `_Pool`, размер 8, `get_db()` возвращает `_PooledDb`, чей `close()` возвращает соединение в пул — идемпотентно). Per-connection PRAGMA: `busy_timeout=5000`, `synchronous=NORMAL`, `foreign_keys`, `mmap_size=256MB`, `cache_size=-65536`; WAL ставится один раз в `init_db` (персистентно). `close_pool()` вызывается при shutdown приложения (lifespan в `main.py`). **Никогда не вкладывайте `get_db()`, держа другое соединение** — пул блокируется на семафоре и дедлокнется. `thread_service.list_threads`/`get_thread_detail` открывают короткоживущие соединения вокруг сетевых скрейпов именно поэтому (pooled-соединение нельзя пинить на многосекундный rate-limited fetch).
- **Запускайте uvicorn только в одном процессе** (в `launcher.py` нет `--workers`): circuit breaker, inflight single-flight локи, in-memory кэш настроек, row LRU и все семафоры — module-level состояние; несколько воркеров его форкнут и поведение будет несогласованным.
- `DATA_DIR` (по умолчанию `/data`) содержит `viper.db` (SQLite, рабочий кэш — растёт с использованием, не фиксированного размера) и `cache/` (скачанные превью изображений). В Docker это том `./data`. Миграций НЕТ — `init_db()` создаёт таблицы при старте; не стирайте `data/` без нужды.

## Устройство backend (неочевидно по именам файлов)
- `app/scrapers/` — парсинг форума: `viper_click.py` (предпочтительный, чистый XML), `forumdisplay.py`/`auth.py` (прямой фолбэк `viper.to` через `curl_cffi` для обхода Cloudflare). `auto_login()` при старте: если заданы env-учётки (`VIPER_USERNAME`/`VIPER_PASSWORD_MD5`) — логинится; иначе `restore_auth()` восстанавливает сессию из `DATA_DIR/auth.json` (cookies + username, chmod 0600; пишется `login()` при UI-логине, удаляется `logout()`). Без network-проверки (оптимистично) — инвалидация всплывёт при первом auth-required действии. В `forumdisplay.py` IMPORTANT-sticky-треды (rules/guidelines/announcements) отсекаются ДО truncation до `PER_PAGE` (12; поиск — `search.py`: `_PAGE_SIZE=60`, `_UI_PER_PAGE=12`, 5 UI-страниц на merge-блок) — иначе в форумах с 7+ такими тредами (например forum 308) юзер видел 5 карточек вместо 12, т.к. downstream-фильтр `_is_non_photoset` (`thread_service.py`) выбрасывал их post-truncation.
- `app/hosts/` — `registry.py` (идентификация хоста по подстроке URL из `HOST_TABLE`, 16 хостов) и `base.py` (HTTP-клиент + все резолверы интерстициальных страниц в `_RESOLVERS`). Добавление хоста = новый резолвер в `base.py` + строка в `HOST_TABLE` (`registry.py`). Pixhost: подстрока `pixhost` покрывает зеркала `.to` **и** `.cc` (оба идентифицируются как `pixhost.to`); `resolve_pixhost` делает чистый URL-transform `show/{a}/{f}`→`img2.pixhost.to/images/{a}/{f}` без HTTP/DNS (апекс `pixhost.to` страдает intermittent DNS-fail). imx.to: `resolve_imx_thumb()` переписывает любой мёртвый thumb-prefix imx.to → живой CDN `https://image.imx.to/u/t/` (чистый URL-transform, без HTTP); thumb-ветка `image_proxy.py` использует его, когда host=="imx.to". `image_proxy` отдаёт каждый тир по схеме **download-then-serve**: upstream-файл сначала попадает в безрасширительный content-addressed дисковый кэш (`_ensure_full_cached`, single-flight на ключ кэша в `_INFLIGHT_LOCKS`), затем выходит как `FileResponse` — честные 502 вместо обрезанных 200, и конкурентные запросы делят один upstream fetch. Upstream content-type'ы запоминаются в `_content_types` (bounded OrderedDict), потому что файлы кэша без расширения. Тир medium (`?size=medium`) — ≤800px WebP (`method=2`), генерируется single-flight через `_ensure_medium`; `_create_medium` использует JPEG `draft()`-декодирование + `exif_transpose`; GIF обходят ресайз (анимация схлопнулась бы в один кадр). При полном сбое резолва/феча `image_proxy._serve_thumbnail` отдаёт thumb как degraded-режим (напр. turboimagehost за CF JS-challenge — full доступен только через thumb-CDN); ПРИМЕЧАНИЕ: `_serve_thumbnail` намеренно НЕ проверяет `is_host_dead` — у СТАРЫХ тредов thumb'ы лежат на том же мёртвом хосте (`s4d*.turboimagehost.com`), и breaker заблокировал бы достижимый thumb; thumb всегда пытается как fallback. Примечание про "Stage 5" в `registry.py` — план рефакторинга, а не отсутствие функциональности.
- Circuit breaker (`hosts/circuit.py`) помечает часто падающие хосты как «мёртвые» → `/api/image/{id}` мгновенно вернёт 502 `Host temporarily unavailable` **без** попытки запроса. Не путайте с реальной ошибкой резолва/феча при отладке 502.
- Фоновая maintenance-задача (`_maintenance_loop` в `main.py`, каждые 30 мин после старта) вызывает `image_proxy.trim_cache_if_needed()` — LRU-по-mtime трим `cache/img`, выполняющийся только когда runtime-настройка `cache_limit_gb` > 0 (по умолч. 0 = без лимита; хардлинкнутые загрузки трим переживают). `/api/stats` отдаёт текущий размер кэша (замер через `asyncio.to_thread`, никогда на event loop) и эффективный лимит (поле `cache_limit_gb`).
- `app/services/` — `zip_service.py` (потоковая ZIP-упаковка на лету через `stream-zip`), `image_proxy.py`, `thread_service.py`, `download_queue.py` (**активная** система загрузок — постоянная SQLite-таблица `download_queue` + `_worker_loop`, поднимающая до `thread_concurrency` тредов параллельно; см. ниже), `fetcher.py` (общий image-fetch pipeline, извлечён из удалённой legacy job-системы: `get_thread_images`/`thread_title`/`resolve_row`/`download_with_retry`/`process_image` — резолв в прямой URL с write-through в БД/LRU + скачивание в content-addressed кэш с ретраями; per-image fetch делит глобальный `download_concurrency` semaphore), `library.py` (лайки + история загрузок: `post_thanks_add/remove` через `_get_securitytoken`, `record_download`/`list_downloads` с prune отсутствующих на диске папок, get/set `downloads_folder`; таблицы `db.py` `liked_threads` + `downloads`), `settings_service.py` (runtime-настройки через `/settings`).
- Роутеры API лежат в `app/api/`, все смонтированы с префиксом `/api` (см. `main.py`). `GET /api/thread/{id}/cover` возвращает обложку + первые 5 превью для hover-карусели. Для массовой подгрузки списка карточек есть `POST /api/threads/covers` (body `{thread_ids:[...]}` → `{covers: {"<id>": <CoverOut|null>}}`) — один запрос вместо N параллельных `/cover`, не исчерпывает пул соединений браузера и не выстраивается за rate-limiter'ом форума. Эндпоинты `/api/image/{id}?size=thumb|medium|full` и `/api/proxy?url=...` (прокси произвольного URL) — большие потоки; Caddy проксирует `/api/*` и `/proxy/*` на uvicorn с `flush_interval -1`. Запрос деталей треда дополнительно запускает фоновые `fire_background_task`-задачи: `prefetch_resolution` (резолвит до 20 прямых URL, чтобы первые просмотры картинок пропустили interstitial-RTT, из `thread_service.get_thread_detail`) и `prewarm_mediums` (скачивает + рендерит medium для первых 6 картинок, из `api/threads.py`). Ответы с картинками несут `Cache-Control: immutable` (год, content-addressed URL).
- `GET /api/search?q=...&forums=...` — это **живой** поиск по форуму (vBulletin Advanced Search, не по кэшу): при scoped-запросе fan-out по батчам leaf-форумов с merge (`scrapers/search.py`). Сортировка теперь монотонная — `_SearchSession._key()` использует post_id/thread_id (раньше парсил human date-string → перемешанный порядок); `search_forum` добавляет защитительный slice-sort. Результаты обогащаются кэшированными обложками. См. отдельный `search_request_limit`.
- **Очередь загрузок** (активная система, `services/download_queue.py` + `api/download_queue.py`): постоянная SQLite-таблица `download_queue` (thread_id PK, title, status[queued|downloading|stopped|done|error], счётчики total/completed/failed, error, added_at; упорядочена по `_rowid_`) + фоновый `_worker_loop` (каждые 2 сек), поднимающий до `thread_concurrency` тредов параллельно (захват через status=downloading перед спавном), собирающий завершённые задачи и сбрасывающий live `_progress` в БД. `_download_thread(tid)` переиспользует `process_image` из `fetcher.py` (делит глобальный `download_concurrency` semaphore с живым просмотром), затем материализует в `downloads_folder` + `record_download` по завершении → status=done. Кооперативный STOP: `request_stop(tid)` → `task.cancel()` → `CancelledError` пойман → status=stopped (возобновление переиспользует кэш); `fetcher.download_with_retry` также закрывает resp + unlink'ит partial-файл при CancelledError (partial не остаётся). `add_to_queue(ids)` идемпотентен и уважает `auto_download` (queued если on, stopped если off). `on_startup()` (вызывается из `main.py` lifespan после `auto_login`) орфанит любые `downloading`-ряды → stopped и стартует воркер. API: `GET /api/download/queue`, `POST /api/download/queue` {thread_ids}, `POST /api/download/queue/{tid}/stop`, `POST /api/download/queue/{tid}/start`, `DELETE /api/download/queue` (очистка всего). Legacy job-система (`POST /api/download/multi` → `/status` → `/retry` → `/zip`) удалена полностью; `api/download.py` теперь отдаёт только разовый стрим `GET /api/thread/{id}/download`.
- Лайки/загрузки (`api/library.py`): `POST/DELETE /api/thread/{tid}/like` (401 если не залогинен; под капотом `post_thanks.php` + securitytoken), `GET /api/liked`, `GET /api/downloads` (items + folder), `POST /api/downloads/folder` (папку репортит Electron при старте/смене).
- Ограничение запросов к форуму — leaky-bucket **на хост назначения** (`HttpClient._rate_for()` в `scrapers/http.py`; см. `request_limit` / `search_request_limit` выше). Исключение: search fan-out использует собственный module-level `_search_rate = RateLimiter(search_request_limit)` в `scrapers/search.py` — один общий лимитер, не per-host. Не дёргайте эндпоинты в циклах.
- uvicorn сам отдаёт собранный SPA из `backend/static/`, если каталог существует (`StaticFiles` на `/`, см. `main.py`) — фолбэк на случай, когда Caddy не используется. В проде этим занимается Caddy из `/srv/static`.
- `_NoCacheHTMLMiddleware` (`main.py`, **чистый ASGI-класс** — не `BaseHTTPMiddleware`, который оборачивает каждый запрос в лишнюю задачу и вредит большим стриминговым image-ответам) шлёт `Cache-Control: no-cache` **только для `index.html`**: Vite выдаёт ассетам content-hashed имена (их можно кэшить вечно), но SPA-shell обязан перечитываться — иначе после апгрейда браузер зовёт старые хэши → 404 → белый экран (Electron дублирует это чисткой кэша при старте, см. ниже).

## Frontend
- Алиас `@` → `./src` (vite + tsconfig). Данные — TanStack Query (staleTime 60 сек, `refetchOnWindowFocus: false`); роутинг — `react-router-dom` v7. Библиотеки состояния нет — состояние это React `useState` + кэш Query + localStorage-хуки (`useViewMode`); следуйте этому паттерну, не вводите стор.
- `npm run build` это `tsc -b && vite build` — TypeScript должен пройти до сборки бандла. Результат сборки — `frontend/dist` (его отдаёт Caddy в Docker). База API переопределяется при сборке через `VITE_API_BASE` (`src/api/client.ts`, по умолчанию same-origin). Поскольку image-ответы кэшируются на год как `immutable`, `client.ts` добавляет к URL картинок cache-bust-параметр `_v=<token>` (токен из sessionStorage); `clearImageCache()` бампит токен И сбрасывает Cache Storage — серверной очистки кэша одной недостаточно, в браузерах остались бы устаревшие immutable-файлы.
- ThreadPage загружает ВЕСЬ тред сразу (`thread.images`, все посты) и пагинует ТОЛЬКО по **12 изображений на страницу** (`IMAGES_PER_PAGE=12`, `frontend/src/pages/ThreadPage.tsx`) — плоский список изображений режется на страницы по 12, каждая выводится сгруппированной по постам (заголовок «Post N» + сетка); индекс поста выводится по порядку первого появления `post_id`. Пост-пагинации больше НЕТ (раньше грузилось 5 постов/страницу через `api.threadPosts`; бэкенд-эндпоинт `/thread/{id}/posts` ещё существует, но UI его больше не вызывает). `VirtualImageGrid`/`react-window` более НЕ используются в ThreadPage (макс 12 узлов — виртуализация не нужна). Числовая пагинация — переиспользуемый `components/Pagination.tsx` (первая/‹/окно 5 страниц/›/последняя), дублируется сверху+снизу на Category/Search/Thread.
- Lightbox (`components/Lightbox.tsx`) предзагружает соседние full-изображения (`new Image()` для ±1) при навигации — браузер дедуплит против immutable-кэша, так что это no-op, если уже было загружено. Предзагрузка **пропускается**, когда включён `navigator.connection.saveData` или effectiveType 2g (`PRELOAD_NEIGHBOURS`, module-level). **Слайд-шоу**: тумблер Play/Pause + слайдер интервала 1–5 сек; когда on, авто-продвижение по картинкам с зацикливанием в конце. Lightbox получает ВЕСЬ плоский список изображений треда — навигация охватывает весь тред, а не только видимые 12.
- **DOM-level keep-alive для CategoryPage** (`App.tsx` + `main.tsx`): `/` и `/forum/:forumId` зарегистрированы в таблице маршрутов только как placeholder'ы с пустым фрагментом; сам CategoryPage — не route-элемент — App детектит `/forum/:forumId` через `matchPath` и всегда держит CategoryPage смонтированной, переключая видимость CSS-классом `hidden`. Поэтому возврат из треда мгновенный (без перезагрузки картинок и скролла). `cachedForumId` хранит последний форум, пока юзер в треде. Outlet рендерит `/thread/*`, `/search`, `/liked`, `/downloads`.
- `RetryImage.tsx` — drop-in `<img>` с авто-ретраем (cache-bust + 3 попытки), красным ✕ fallback и кнопкой ручной перезагрузки на hover. Если в `className` уже есть position-утилита (absolute/relative/fixed/sticky), свою `relative` НЕ добавляет (Tailwind ordered `.relative` after `.absolute`, что ломает hover-карусель — см. `positionClass` helper). Регистрируется в глобальном `ImageRefreshProvider` для batch-перезагрузки упавших изображений.
- **Карточки используют `size=thumb`** (50-200KB) изначально, НЕ medium — на карточках thumb хватает, а backend'у не нужно скачивать full (5-20MB) для Pillow-ресайза. `fetchPriority="high"` на cover, `"low"` на previews (eager; camelCase-проп — React 18.3+ поддерживает `fetchPriority` нативно, старым 18.x нужен lowercase-атрибут). В сетке `ThreadPage` — medium (там показ крупнее). В Lightbox — full + preload соседей через `new Image()`.
- **Карточки-сетки** (`CategoryPage`/`SearchPage`/`LikedPage`/`DownloadsPage`): адаптив `grid-cols-2 sm:grid-cols-3 lg:grid-cols-3 xl:grid-cols-4`, обложки landscape `aspect-[4:3]` с `object-contain` (вертикальные картинки — с боковыми полосами, не обрезаны). `RetryImage` форвардит `object-fit` из className во внутренний `<img>` (по умолчанию `object-cover` — см. `objectFitClass` helper рядом с `positionClass`). Сердечко-лайк сидит **сверху-слева** на карточке через `useLikes` hook (optimistic, `POST/DELETE /api/thread/{tid}/like`); кнопка скачивания — **сверху-справа** (добавляет тред в очередь через `POST /api/download/queue`). `ThreadCard` определён инлайн в `CategoryPage` и реюзается в SearchPage/LikedPage; DownloadsPage рендерит собственную инлайн-карточку (без кнопок лайк/скачать, `size=medium`, `refetchOnMount: "always"` — backend prun'ит удалённые папки на GET). Обложки карточек приходят через `hooks/useOrderedCovers.ts`: ОДИН batch `POST /api/threads/covers` для тредов без серверно-закэшированных `image_ids` (треды, у которых они есть, засеиваются мгновенно, без запроса); упавший/прерванный batch резолвит pending-записи в `null`.
- **Wave-based загрузка карточек** (`hooks/useWaveLoader.ts`, координатор живёт в `CategoryPage`/`SearchPage`; сам `ThreadCard` определён **инлайн** в этих страницах, а не отдельным файлом): загрузка синхронизирована по **всем карточкам страницы**, а не per-card. `MAX_SLOTS=5` (cover=slot 0 + 4 превью). Координатор держит `step` 0..9 и продвигает его, когда **90%-кворум** карточек репортит завершение текущего слота (`reportCardDone`, `quorumCount` = ceil, min 1 — один мёртвый хост больше не вешает всю страницу); 8-сек таймаут (`WAVE_TIMEOUT_MS`) страхует от зависшего слота. **Phase 1 (thumb, step 0–4):** slot 0 всех карточек параллельно → slot 1 → …; внутри одной карточки — строго последовательно. **Phase 2 (medium, step 5–9):** тот же wave-pattern для medium **только slot 0 (обложки)**, через фоновый `new Image()`-проб; слоты > 0 авто-репортят, их medium откладывается до hover карточки (отдельный hover-проб ДЕЙСТВИТЕЛЬНО чистится через `probe.src=""` — не путать его с wave-пробом). Когда medium скачан (в browser cache), видимый `<img>` переключается thumb→medium мгновенно + короткая flash-анимация (`img-swap-flash`, флаг `swapped` в `useImageRetry`). Wave стартует только когда все обложки получены (`coverById.has` для каждого `t.id`). `useImageRetry` НЕ сбрасывает `loaded` при смене src — браузер держит thumb, пока грузится medium (нет белого flash); упавший medium-проб оставляет thumb видимым. Никаких backend job'ов/SSE — medium on-demand через `/api/image/{id}?size=medium`. **Wave-эффект НЕ ДОЛЖЕН прерывать in-flight пробы при продвижении step** (никакого `probe.src=""`-клинапа): при 90%-кворуме wave регулярно продвигается, пока проб самой медленной карточки ещё в полёте, и его прерывание оставило бы слот навсегда незагруженным (никто не возвращается к ранним слотам) — вечный спиннер/пустое превью. Пробу разрешено догрузиться в фоне (`finish()` отмечает слот готовым, когда она приземлится; `pendingProbeRef` дедуплицирует между повторами эффекта, `aliveRef` глушит репорты после unmount).
- `App.tsx` prefetch'ит `settings` и `stats` queries при маунте — чтобы Settings-модалка открывалась мгновенно даже когда image-стримы заняли все 6 соединений (TanStack Query dedup'ит с модалкой).
- **Хедер**: кнопка Back (`navigate(-1)`) заменяет старую надпись "Browse Photo Sets" — глобального заголовка в хедере больше нет.
- **Панель очереди загрузок** (`components/DownloadQueuePanel.tsx`): кнопка тулбара с бейджем активных → dropdown-таблица (заголовок, бейдж статуса, [completed/total], прогресс-бар, STOP/START построчно — START скрыт, когда done, кнопка Clear-очереди). Поллинг каждую 1 сек, пока есть активные (`queued`/`downloading`) элементы. **Заменила** старый `MultiDownloadModal` non-dismissable попап (модалка удалена).

## Electron / десктоп
- `electron/main.js` (основной режим для конечных юзеров по README) спавнит бэкенд как child-процесс и рендерит SPA в `BrowserWindow`; `electron/preload.js` (contextBridge) экспозит `window.electronAPI` (`isElectron`, `showInFolder`, `openPath`, `chooseDownloadsFolder`). Запуск: `python -m app.launcher --no-gui` в cwd `backend/`.
- **Повторное использование бэкенда**: Electron сначала стучится на `/api/health`; если бэкенд уже слушает (например, systemd-сервис из deb/rpm), он НЕ спавнит второй (иначе `address already in use`). На close убивает только тот процесс, что сам породил (`startedBackend`).
- **Скачивания в папки (десктоп)**: `session.defaultSession.on('will-download')` → `item.setSavePath(downloadsDir/<filename>)` без диалога (имя файла из Content-Disposition; папка по умолчанию `~/Downloads/ViperGirls`, переопределяется через `dialog.showOpenDialog` по IPC `choose-downloads-folder`, персистится в settings `downloads_folder`). IPC `open-folder` → `shell.openPath` с `fs.existsSync`-проверкой → graceful `{ok,missing}` (фронт показывает алерт + инвалидирует список для prune). IPC `show-in-folder` → `shell.showItemInFolder` (legacy).
- `backend/app/launcher.py` — единый серверный entrypoint для десктопа и systemd (`packaging/common/run.sh`). `VIPER_HOST`/`VIPER_PORT` (по умолч. `127.0.0.1:8000`). `--no-gui` теперь **no-op** (server-only всегда) — оставлен для обратной совместимости.
- **Бандлинг Python отличается по ОС** (gotcha при отладке нативных сборок): на **Linux** бандл ставит `PYTHONHOME`+`PYTHONPATH` на свой runtime; на **Windows** embeddable Python использует `python312._pth`, который **игнорирует `PYTHONPATH`** — путь к backend'у вшит в `._pth` на этапе сборки (см. `packaging/docker/windows/Dockerfile`). Не ставьте `PYTHONHOME` на Windows-embeddable — ломается.
- Меню скрыто (`Menu.setApplicationMenu(null)`); DevTools — **F12** через `before-input-event`. `WM_CLASS` пинится в `vipergirls-viewer`, чтобы taskbar/док матчил на `.desktop` и иконку (`nativeImage`; bare-path на Linux ненадёжен).
- При старте Electron чистит HTTP-кэш Chromium (`session.clearCache()`) — иначе закэшированный `index.html` от прошлой сборки ссылается на старые content-hashed хэши → 404 → белый экран. Бэкенд дублирует это `_no_cache_html` middleware.
- Нативная упаковка (exe/deb/rpm/AppImage) — кросс-компиляция из Linux через Docker, скрипты в `packaging/scripts/` (подробности в `docs/PACKAGING.md`). Отдельный процесс от Docker-образа для self-host.

## Соглашения / подвохи
- Юнит-тесты бэкенда лежат в `backend/tests/` (pytest + pytest-asyncio, `asyncio_mode=auto` через `pytest.ini`, зависимости в `requirements-dev.txt`). Покрывают **только чистую логику, без сети**: схему/coercion/персистентность настроек, компоновку proxy-URL + `redact_proxy`, чистые URL-transform резолверы (imx/pixhost), реестр хостов, рецикл соединений пула SQLite и rate-limiter. `conftest.py` указывает `DATA_DIR` на временный каталог **до любого импорта `app.*`** (он читается на уровне модуля), чистит таблицу `settings` перед каждым тестом и пересоздаёт `asyncio.Lock` в settings_service (каждый тест получает новый event loop). Запуск: `cd backend && pip install -r requirements.txt -r requirements-dev.txt && pytest`. Тестов фронтенда НЕТ, конфигурации lint нет (кроме `tsc -b`). CI: `.github/workflows/build-macos.yml` (push в `develop`, PR, ручной `workflow_dispatch`; только arm64 — `macos-14`, Intel выпилен): macOS-only **smoke-test gate** — `frontend npm run build`, `pip install`, затем `python -m app.launcher --no-gui` должен отдать `GET /api/health` 200 за 60 сек; PyInstaller-бандл best-effort (`continue-on-error`); и `.github/workflows/tests.yml` (те же триггеры; Ubuntu — совпадает с платформой Docker-образа: pytest + сборка фронтенда + тот же офлайн health smoke). Стартап бэкенда офлайн-безопасен (нет учёток + нет `auth.json` → `auto_login`/`restore_auth` — no-op'ы, health доступен без сети) — тот же рецепт годится для локальной верификации. (Это git-репозиторий, ветка `develop`.)
- **UI-тестирование вручную**: агент не может сам кликать по UI — он даёт пошаговые инструкции (что нажать, что должно произойти, какие логи собрать), а человек проверяет в запущенном приложении и возвращает результат/логи. Backend-изменения верифицируются через `pytest` (юнит-скоуп) + `py_compile` + `import app.main` + изолированные скрипты на test-БД (`DATA_DIR=/tmp/opencode/...`), frontend — через `npm run build` (`tsc -b && vite build`).
